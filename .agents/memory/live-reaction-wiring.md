---
name: Live overlapping reaction wiring
description: Non-obvious decisions for extending the AI overlapping-reaction mechanic to a new exchange type
---

- **Reactor selection differs by format.** Multi-persona exchanges react via a bystander (a persona other than the two speakers); genuine 1-on-1 formats have no bystander available, so the reaction there comes from the other party in the exchange instead. Pick the gating rule (mode-based vs tone-based) already used by that exchange type's other calls, don't assume one scheme fits every endpoint.
- **A reaction must be scheduled off the actual playback start of the line it's meant to overlap**, not fired as soon as that line is queued — queueing only reserves a slot, it doesn't mean nothing is still playing ahead of it.
- **Screens that look like copies of each other (e.g. multiple call-in UIs hitting the same endpoint) are usually separately implemented, not shared code.** Wiring a new mechanic into one does not wire it into the others — check every caller of the endpoint being changed.
- **Off-queue "interrupt track" audio (played via a dedicated function outside the normal TTS queue, e.g. playInterruptionAudio) can only safely hold one clip at a time.** Firing a second off-queue clip (e.g. an immediate retort) right after the first only awaits "sound created", not "playback finished" — so the two clips talk over each other and stomp each other's cleanup/volume-restore state. If a second off-queue clip must follow the first, give the function an onDone-style completion callback (fired from its cleanup, not from creation) and await real completion before firing the next one, or fire it through the actual owning gate (e.g. skip an AI round-trip and speak the canned line immediately/deterministically) rather than guessing a fixed delay.
- **Canned/static reaction text (not AI-generated) bypasses server-side output sanitization.** Server routes strip markdown stage directions like `*laughs*` from AI-generated dialogue before speaking it, but hardcoded client-side catalogs sent straight to a TTS endpoint do not go through that same cleanup — so asterisk-wrapped stage directions in canned lines get read aloud literally. Strip stage directions at the lowest shared TTS call point (e.g. the client's playTTS wrapper), not per-catalog, so every caller is covered.
